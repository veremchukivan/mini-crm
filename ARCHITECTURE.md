# Architecture Notes

## Чому Laravel 12

Laravel 12 дає стабільний сучасний стек із новим bootstrap API, сильним Eloquent, зручними Form Request, Resource і зрозумілою структурою для Blade + API в одному моноліті. Для цього ТЗ це швидше й чистіше, ніж дробити все на окремі сервіси.

## Чому Spatie Laravel Permission

- стандарт де-факто для ролей і permission у Laravel-проєктах
- добре інтегрується з middleware `role`, `permission`
- дозволяє розвести рольовий доступ від бізнес-логіки контролерів

У проєкті ролі `manager` і `admin` отримують права `tickets.view` та `tickets.update`.

## Чому Spatie Media Library

- зберігає вкладення як окремий bounded context навколо моделі
- дає єдину точку роботи з файлами без власних таблиць/полів на заявку
- добре тестується через fake storage

ТЗ прямо вимагає прив’язку файлів до заявки тільки через Media Library, тому окремі файлові поля в `tickets` не використовувались.

## Чому Actions

Логіку створення заявки і підрахунку статистики винесено з контролерів у:

- `CreateTicketAction`
- `BuildTicketStatisticsAction`

Це зберігає контролери тонкими, а бізнес-правила концентрує в окремих класах, що простіше тестувати й підтримувати.

## Чому Form Requests

Form Request закривають:

- валідацію API-входу
- валідацію фільтрів адмінки
- валідацію зміни статусу

Так контролери не перетворюються на змішані класи з HTTP- і бізнес-логікою.

## Чому enum для статусів

`TicketStatus` реалізовано як native PHP enum, тому:

- немає розкиданих строкових літералів по коду
- простіше будувати select, badge і перевірки
- нижчий ризик помилок при зміні статусу

## Чому customer + ticket

Клієнт і заявка розділені навмисно:

- `customers` містить контактну сутність
- `tickets` містить звернення й життєвий цикл заявки

Це відповідає CRM-моделі та дозволяє одному клієнту мати кілька заявок у різні дні.

## Денний ліміт заявок

Обмеження “не більше однієї заявки на добу з одного email або номера телефону” реалізоване в `CreateTicketAction`, а не тільки на рівні БД. Причина проста: правило залежить від часового вікна, а не від постійної унікальності запису.

## Чому Blade для UI

Для цього обсягу задачі Blade-панель простіша за SPA:

- швидше підняти
- менше інфраструктури
- достатньо для фільтрації, перегляду й оновлення статусу

Віджет винесений в окрему Blade-сторінку, готову до вставки в iframe.

## Чому статистика через scopes + Carbon

ТЗ прямо вимагає Carbon + Eloquent scopes. Тому в `Ticket` додані:

- `scopeCreatedToday`
- `scopeCreatedThisWeek`
- `scopeCreatedThisMonth`

Підрахунок зібраний через окремий action, а не дублюється по контролерах.
